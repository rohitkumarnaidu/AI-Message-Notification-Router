# API Reference

This document outlines the API endpoints, data models, and execution modes for the Message Notification Router.

## FastAPI Backend

The backend is built with FastAPI, providing robust and well-documented REST endpoints.

**Base URL:** `http://localhost:8000`

### Endpoints

#### `GET /api/messages`
Returns all routed messages.

**Response Shape:**
```json
{
  "status": "success",
  "data": [
    {
      "message_id": "msg_001",
      "message_text": "Project meeting moved to 3 PM.",
      "action": "notify",
      "message_type": "work",
      "reason": "High relevance and during working hours.",
      "confidence": 0.95,
      "evidence_message_ids": ["msg_000"]
    }
  ]
}
```

**Example Request:**
```bash
curl -X GET http://localhost:8000/api/messages
```

#### `GET /api/stats`
Returns aggregate routing statistics.

**Response Shape:**
```json
{
  "status": "success",
  "stats": {
    "total": 110,
    "notify": 45,
    "digest": 40,
    "mute": 25
  }
}
```

**Example Request:**
```bash
curl -X GET http://localhost:8000/api/stats
```

#### `GET /docs`
Interactive Swagger UI for testing the API endpoints, auto-generated by FastAPI.

#### `GET /redoc`
ReDoc UI for API documentation, auto-generated by FastAPI.

## Output CSV Schema

The router processes messages and outputs a structured CSV. The schema consists of 6 columns:

1. **`message_id`**: A unique identifier for the message.
2. **`action`**: The routing decision. Allowed values: `notify`, `digest`, `mute`.
3. **`message_type`**: The category of the message. Allowed values: `work`, `personal`, `promotional`, `alert`, `unknown`.
4. **`reason`**: A brief explanation of the routing decision.
5. **`confidence`**: A float between `0.0` and `1.0` representing the confidence of the decision.
6. **`evidence_message_ids`**: A JSON string or pipe-separated list of related message IDs used as context.

## Error Handling & Execution Modes

The router features a structured pipeline with 9 execution modes for graceful degradation:

1. **`DETERMINISTIC_DIRECT`**: Purely rule-based routing when signals are unequivocally strong.
2. **`LLM_FULL_CONTEXT`**: LLM-based routing using all available context and extracted features.
3. **`LLM_REDUCED_CONTEXT`**: LLM-based routing using a compressed version of the context if the full context fails or is too large.
4. **`LLM_BASIC`**: Fallback to a basic prompt with minimal context.
5. **`LLM_DIRECT_RETRY`**: Direct retry of the LLM call upon transient failure.
6. **`LLM_FALLBACK`**: Utilizing an alternative LLM provider/model if the primary fails.
7. **`DETERMINISTIC_FALLBACK`**: Fallback to rule-based routing if all LLM attempts fail.
8. **`DETERMINISTIC_BASIC`**: Highly simplified rule-based routing to ensure a valid response is generated.
9. **`DETERMINISTIC_FINAL_FALLBACK`**: The ultimate safety net returning a safe default action (e.g., `digest` or `notify`) if everything else fails.

When external APIs (LLMs, OCR, ASR) are down, the system gracefully degrades through these modes to guarantee a decision is made.

## Authentication

**Note:** Currently, there is no authentication implemented on these endpoints as they are designed for internal and demo use.

**Enterprise Recommendation:** For production deployments, it is recommended to add JWT or OAuth2 authentication via FastAPI security middleware to secure the `/api/*` routes.
